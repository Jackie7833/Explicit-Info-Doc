# Query 构建与验收

本文件是第五部分十道 Showcase 与文档交付后完整评测集的共同 Query 规则。两条链路使用同一套硬性限制、自然度要求、任务设计和验收口径；不同之处只在输出规模、列结构和配额来源。Query 规则优先于历史题目、版式示例和凑题量要求。

凡涉及 Query 文本、单轮边界、自然度、动态信息、附件指代、逐题标签、环境信息或 Query 验收，均以本文件为唯一细则来源。用户场景与 BMK 规则只负责规划任务空间、真实使用机会和配额，不在别处重新定义 Query；文档规则只负责章节结构与版式。出现重复描述时，以本文件为准。

## 与 BMK 规划的接口

BMK 规划只读取本节判断“是否有可出题空间”，不生成具体 Query，也不替代逐题验收：

- BMK 方案须在单轮、当前确认范围、真实业务目标、可读取材料和可复现边界下设计广度、厚度、深度的任务空间；不能依赖前轮对话、未来实时结果、评测者提示或虚构业务链路来填配额。
- `user_scenarios` 与 `bmk_plan` 是 Query 的上游输入。Query 生成应实例化已确认的维度、主用户场景、能力和任务场景配额，不得静默增删场景、改写能力范围、改动题量或把辅助标签当成主归属。
- 若某一配额在这些约束下无法形成足够真实且有考察价值的题目，应返回 BMK 规划阶段重新调整任务空间或配比并再次确认；不得在出题阶段放宽单轮/动态/业务真实性限制、制造复杂度或强行改标签凑数。
- Query 阶段发现的是单题问题（措辞、材料、自然度、Rubrics 或证据不足）时，只修订或替换该题；只有任务空间或配额不可行时才回到 BMK 规划。

## 依据与适用边界

自然度部分依据包内 [RealUserSim 真实性参考提炼](../materials/方法参考/RealUserSim-真实性参考提炼.md)，必要时回读原始论文 [2605.20204v1.pdf](../materials/方法参考/2605.20204v1.pdf)；表达组织和用户话术的校准也参考 [语言模型Benchmark自然度与设计参考.pdf](../materials/方法参考/语言模型Benchmark自然度与设计参考.pdf)。这些材料用于判断用户是否会这样说、信息如何组织、语气、信息密度和长度是否符合语境。

RealUserSim 研究基于 WildChat 英文多轮轨迹的 profile-grounded user simulation。本文只把它作为 Query 表达形式、信息组织、信息密度、术语熟悉度和互动节奏的观察参考；它不提供当前三方服务的中文用户分布、业务需求、能力范围、BMK 配比、难度或评分阈值。论文中的五个保真维度是观察视角，不是每道题必须具备的特征，不转成固定风格配额、人格画像或独立评分维度。意图密度可以在目标前置与信息分散之间变化，但 Explicit Query 仍须单轮自足，必要事实不能依赖后续追问。

论文中的多轮模拟、用户画像、固定权重、模拟器或用户数据任务不直接转入 Explicit Query；论文也不能替代当前 PRD/评测说明文档对能力范围的确认，不能单独证明业务需求、产品能力、动态事实或 BMK 配比。

## 一、硬性限制

### 1. Explicit 单轮

- 每道题只有一条自足的用户请求。完成目标所需的信息必须来自本条 Query、本轮附件或可读取的预置业务资源。
- 不得依赖前轮聊天、用户后续补充、被测模型先追问再继续、用户确认后再执行，或“刚才那份/前面提到的”这类不可读取的上下文。
- 单轮不等于单步骤：允许模型在同一轮内多次调用工具、使用上一步结果继续执行、组合条件和进行推理；但 Query 必须一次性交代任务终点及必要条件。

### 2. 范围与能力边界

- Query 只能考察当前已确认的一级能力、覆盖的用户需求、能力范围和用户场景，不新增 PRD/说明文档未支持的功能、对象或渠道。
- Query 中的目标、对象、必要参数和预期结果必须能映射到已确认范围；不把登录、鉴权、授权、断网反馈、意图识别、信息收集或多轮追问等工程测试/产品策略单列为业务功能。
- 允许一个 Query 覆盖多个真实相关能力，但不能为了多标签、厚度或深度拼接没有共同业务目的的操作。

### 3. 不构建时效性题目

- Showcase 和完整评测集不构建依赖具体未来日期、实时场次、余票、价格、库存、上映状态或即时路线才能判分的题目。例如“订 11 月 28 日晚上深圳龙华万象城上映的《阿凡达 3》”不纳入评测题。
- 如果本期能力只能通过动态资料呈现，必须改用带时间戳的固定附件或预置快照，把考察点放在对材料的理解、比较或执行，不把实时变化本身作为答案依据；无法稳定复现时改题或替换。
- 业务依据可以检索当前官网和用户反馈来判断需求是否真实，但当前场次、价格、余票等动态结果不直接写入 Query 作为固定答案前提。

### 4. 真实业务目标与可观察终点

- Query 必须表达用户真实要完成的业务任务，并能说明完成后有什么可观察结果或收益；不能只是创建空白文档、无业务目的发消息、单纯暂停/播放或验证接口通断等零一测试。
- 简单服务可以保留真实且有业务价值的单操作，但不能因此大量生成只替换对象名称的同质题。
- 不把评测术语、内部能力名、原子 API、评分要求或模型内部推理写成用户指令；用户只有在真实需要区分服务时才自然提及 MCP、CLI、Skill 或服务名称。

### 5. 材料、附件与预置资源

- 附件、邮件、订单、文档、歌单等可以作为本轮可读取材料或预置业务资源，但材料必须真实存在、内容可见并足以支持题目判断。
- Query 不得以“附件有什么”“附件是什么”“读取附件内容”“本轮附件”等实现/评测脚手架方式指代材料。应按业务内容或用途自然表达，例如“我把到场时间和返程安排发你了”“根据我发的安排文档算一下”。只有盘点文件本身是用户目标时才例外。
- 不得用自然措辞掩盖缺少材料、不可读取资源或未准备的状态；必要材料缺失时补齐环境或改题。

### 6. 不写评测者提示或结果承诺

- Query 不得在句末追加“不要承诺真的会加场”“不要告诉用户会成功”“仅用于测试”“不要泄露答案”等评测者/系统口吻的免责声明、负向边界解释或评分提示。
- 这类要求放在环境信息、通过标准或内部验收记录。用户真实提出的业务限制，例如“不要重复发送”“只保留南京的结果”，可以自然保留。

### 7. 信息真实、完整且不藏结论

- 保留完成任务必需的对象、条件、时间范围、地点、附件指向和结果要求；不能把关键任务条件全部藏到 Rubrics 或环境说明中，导致 Query 单独无法理解。
- 环境信息提供可观察材料和初始状态，预期结论和评分条件留在 Rubrics；Query 不提前泄露答案，也不要求模型展示内部推理。

## 二、自然度要求

### 1. 像真实用户会发送的话

- Query 应接近真实语音转写或聊天请求，允许自然省略、代词、连接词、同义说法和不同正式程度，但必须仍能判断目标、对象、必要条件和结果。
- 不为了“像口语”机械加入错别字、重复、表情、口头禅、夸张情绪或不必要的语病；自然度不是信息缺失。

### 2. 信息位置灵活

- 不固定把日期、地点、对象、任务、附件或工具名称放在句首、句尾或某个固定字段位置。
- 可以采用场景先行、目标先行、对象先行、附件指向、结果先行或直接请求等结构；变化应符合当前服务的真实表达习惯，不能只机械替换开头。
- 信息密度和意图前置程度可以变化：有的 Query 先说目标，有的先交代处境或材料；变化只体现在组织方式和表达长短，完成任务所需的事实仍须在本轮提供，不能模拟逐步透露信息来诱发追问。
- 工具名和服务名不默认前置。用户真实需要区分服务时才自然出现；不要把 MCP、CLI、API 或原子能力名称强塞进日常话术。

### 3. 任务事实与表达方式分开

- 自然化前后必须保持目标、对象、必要条件、权限、结果和通过标准一致；不能为了口语化删掉关键限制、增加动作、代用户授权或替用户承诺结果。
- Query 不把完整执行步骤、工具调用顺序或全部 Rubrics 条件逐字写出来；用户只交代真实目标和必要要求。

## 三、维度、标签与题目组织

- Query 的维度标签单选“广度”“厚度”或“深度”，依据实际任务结构判断，不按表格位置决定。
- **广度**：短链路、少步骤，通常覆盖一个或两个相关原子能力；先保证本期能力和主要任务场景的有效覆盖，不机械地为每个原子能力单独出题，也不大量生成直接查询或零一题。可以加入有业务依据的边界结果，但边界不是独立功能。
- **厚度**：一条请求驱动真实业务中的多步骤长链路，前一步结果自然成为后一步输入；条件、对象、参数和状态必须保持一致，不用无关操作或重复步骤制造复杂度。
- **深度**：模型基于本次 Query、附件或预置资源进行理解、消歧、关联、规则应用、权衡或判断，再落实到结果；可以只涉及一两个原子能力，关键是有实质推理，不是单纯链路更长。
- 用户场景标签单选；一级能力和 4.3 任务场景标签可按实际覆盖多选，第一个标签是主归属并用于统计。标签不能为了凑覆盖而乱加，首任务场景必须属于首能力。
- 题目可以跨能力或场景，但必须有共同业务目标；不能通过更换人名、歌曲、商品、地点或措辞制造同质题。

## 四、环境信息与 Rubrics

- 公共账号、工具和默认登录状态集中写在第五部分表格前的统一环境说明；单题环境只补本题差异。
- Showcase 没有特殊准备时环境信息写“—”；完整评测集无特殊准备时该字段留空。两条链路都只写必要的对象、关键内容和初始状态。
- Rubrics 使用简洁的 `R1: …`、`R2: …`；全部必要条件满足才记 1，任一必要条件不满足记 0。Rubrics 写可观察结果，不复制 Query 之外的内部提示，不把用户后续回复、模型内部推理或评测者免责声明作为成功条件。

## 五、两条链路的共同规则与差异

### Showcase

- 固定输出 10 道、五列表格：用户 Query 示例、能力标签、环境信息、指令类别、通过标准。
- 采用 4 道广度、3 道厚度、3 道深度展示代表性 Golden Case；该比例独立于完整 BMK 配比，不得用改标签或虚构复杂度凑数。
- 十道题只承担代表性展示，不要求包办完整覆盖；每道仍必须通过本文件的全部硬性限制和自然度验收。

### 完整评测集

- 文档交付后，只有在用户确认 Showcase 和修改方向后才开始生成。
- 保留用户认可的好题，以修改后的 Showcase 为示例、以对话反馈为修改方向，按已确认 BMK 配额补齐剩余题目；不能把 4/3/3 直接复制成全集比例。
- 使用七列：Query、维度、场景分布、用户场景、能力、预置信息、Rubrics。Query 沿用本文件全部规则，不因批量生成而放宽单轮、自然度、业务价值或时效性限制。

## 六、统一验收清单

每道题先检查硬性限制，再检查自然度和题目质量：

1. 是否能在一条用户消息内完成，不依赖前轮聊天、追问或后续确认。
2. 是否只使用当前已确认范围，目标、对象和结果是否可映射到能力及用户需求。
3. 是否存在实时/临近日期、场次、余票、价格、库存或即时路线依赖；有则改用固定快照或替换。
4. 是否有真实业务目的、可观察终点和足够的能力考察价值。
5. 是否使用了真实、可读取的附件/预置资源，并按业务内容自然指代。
6. 是否出现评测者免责声明、结果承诺、接口术语或固定模板式开头。
7. 日期、地点、对象、任务和工具名称的位置是否与其他题有自然变化，是否只是机械替换实体。
8. 维度和标签是否反映实际任务结构，Query、环境信息与 Rubrics 是否一致。

Showcase 与完整评测集均执行同一清单；差异只体现在展示数量、表格列和配额来源。脚本检查字段、结构、数字和状态，模型负责语义、自然度、业务价值和整体多样性验收。
