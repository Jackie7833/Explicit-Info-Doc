# 文档撰写与验收

只有范围准备完成、用户场景和完整 BMK 方案均已确认并保存后，才进入本阶段。按本次动作读取下表中的小节；可用 `read_stage.py` 定位对应原文。状态与输出链接复用见[应用连接与状态管理](应用连接与状态管理.md)，不因链接出现而全文加载无关流程。

第五部分 Query 的单轮边界、自然度、动态信息、材料指代、标签和逐题验收统一以 [Query 构建与验收](Query构建与验收.md) 为准；本文件只定义文档章节、字段、版式与交付验收。第五部分与文档交付后的完整评测集必须使用同一份 Query 规则。

## 按动作定位

| 本次动作 | 本文件所需部分 | 跨文件依据及材料 |
|---|---|---|
| 首次撰写完整文档 | 输入/标题及第一至第六部分，按章节逐组读；最后回读验收 | 先完成连接中的画板权限检查；按参考索引读主版式，案例和原件按具体需要补读 |
| 新建或改写十道示例 | 五、题目示例（含字段、Golden Case验收） | Query 构建与验收（与完整评测集共用）；共用总纲（评测边界、题目质量、整体质量）与完整维度判定（含可行性）；业务依据：来源选择与补查；对应方法参考及必要历史题目 |
| 仅精简既有通过标准 | 五、题目示例的字段/验收；回读验收 | 当前Query、环境、全部必需成功条件及既有质量记录；连接中的修订与输出契约，不重新加载全套方法原件 |
| 仅绘制或修订画板 | 三图同一画板 | 当前确认方案；连接中的权限、输出证据；三张参考图，不加载题目样例或全文版式PDF |
| 其他局部文案/格式修订 | 输入执行及受影响章节；回读验收 | 连接中的变更规则；仅改动影响相关判断时补读对应来源或参考 |
| 验收与交付 | 回读验收、修正与交付 | 连接中的文档、画板和完成证据；实际正文及远端预览 |

## 输入、参考与执行

- 正式文档/画板写入前，先执行[交付前的画板写入授权](应用连接与状态管理.md#交付前的画板写入授权)：已有有效权限复用，缺少时先向用户申请并等授权完成；不能先交付完成版再补权限。该检查位于 BMK 确认之后，不增加来源阶段的安装或全域授权预检。
- 使用同一确认版本的 `evaluation_scope`、`scope_basis`、`user_scenarios`、`bmk_plan`，所有题量由同一规划条目汇总。PRD 使用真实确认快照；说明文档使用规范后的来源范围，并保持用户已确认的一级能力、用户需求名称及顺序，不能再要求不存在的 PRD。
- 主版式为本地“什么值得买”评测说明 PDF，其余九份为副版式；第五部分参照 QQ 音乐五列表格；三张图以整体布局 JPG 为主要视觉依据，另两张用于细节。
- 优先顺序：用户最新明确要求及本包已确认规则 → Handbook/自然度与设计/RealUserSim 方法和提炼 → 什么值得买主版式 → 九份副版式 → 历史评测集及参考图。固定表头、文案、列表、引用与标题层级优先于案例。此处是冲突优先级，不是每次都读取全部材料的清单。
- 历史参考全部从包内读取，不登录历史飞书链接。历史业务、题量和配比不作本期数据。
- 飞书正文用 `lark-doc` 的实际文档工作流创建、更新和回读；使用原生标题、表格、单元格无序列表及引用块，不能以纯文本符号或截图冒充可编辑正文。画板操作按下节 Lark 路由。
- 不在文档中展开内部状态、模型推理过程、脚本或安装信息。公开资料支持的场景判断保存实际来源，合理安排可点击出处；不将规划占比写成实测调用比例。

## 标题与标题层级

文档标题：`〈评测对象名称〉 〈工具类型〉 IWE-Explicit 〈版本〉 Info`。

对象名称不重复带工具类型，工具类型按当前实际 MCP、CLI、Skill 等填写。版本默认 `v1`，用户指定则采用，续接沿用既定版本；文案/场景/配比调整不自动升级版本。

以下六个使用飞书原生 H1：

1. 一、评测目标
2. 二、评测范围
3. 三、评测标准
4. 四、数据分布
5. 五、题目示例
6. 六、评测集链接

`4.1 用户场景`、`4.2 广度、厚度、深度指令说明`、`4.3 题目分布`使用原生 H2，保留编号及文字。

## 一、评测目标

固定句式：

> 评测 Agent 在明确需求下通过「〈评测对象名称〉」 〈工具类型〉 的方式完成〈本期能力列表〉等能力。

此处展示为句式示意，写入正文时用普通段落。能力列表依评测范围第一列顺序用顿号连接，每项一级能力出现一次。

## 二、评测范围

PRD 分支由模型根据 PRD 与确认范围撰写能力范围，允许归纳、重组相关事实，说明对象、操作、用户看到什么结果算完成及限制；对应确认的一、二级能力，不增加/遗漏/编造。说明文档分支使用已规范的范围及共用边界，不从其目标、评分、示例等章节扩写。

能力范围采用简洁、正向的短要点，直接说明用户能完成什么、得到什么；避免大段解释和反复的“不支持／不得／不能”。保留必要的具体数量、输出及完成条件；完整技术限制与共用边界留在内部 scope_basis，适用时落实到单题环境和通过标准，不将原文所有限制堆进正文。技术支撑功能写成其所服务的业务任务中的前置条件或可观察要求，不凭内部技术术语扩写独立用户能力；每条关键约束能回溯当前来源。

按以下顺序：

1. 上方原生引用块，含来源链接及范围说明。
2. 三列表格。
3. 下方原生引用块，列本期不包含内容。

PRD 上方引用显示可点击“〈评测对象名称〉 PRD”，根据实际选择写：

| 当前范围 | 引用说明 |
| --- | --- |
| P0，全部覆盖 | 本期包含全部 P0 功能 |
| P0，部分覆盖 | 本期包含部分 P0 功能 |
| 全部功能，全部覆盖 | 本期包含 PRD 全部功能 |
| 全部功能，部分覆盖 | 本期包含 PRD 部分功能 |

说明文档上方引用显示“〈评测对象名称〉评测范围来源”及实际链接/本地引用，写“本期范围依据来源文档的评测范围整理”；不称 PRD，不虚构 P0。

表头固定：`能力 | 覆盖的用户需求 | 能力范围`。

- 每个一级能力一行，名称与顺序照录最终范围。PRD 前两列照录 PM 确认名称，不能在转录时擅自改写；说明文档使用通过真实业务功能判断后整理的范围，不重新恢复来源中的工程或策略类能力。
- “覆盖的用户需求”必须沿用已确认的真实用户目标标签：使用简短词组/短语，优先动词＋对象或结果，不能在转录时退化为纯名词、功能测试点、接口动作或意图识别/信息收集等实现手段。用户需求描述用户要完成什么，具体条件、边界和完成标准放入“能力范围”。
- 第二、第三列各自为原生无序列表，单项也用列表。两组条数独立，不作一一对应。
- 内部保留共用业务边界以支撑设计；正文不单列“共用业务边界”标题、段落或列表，也不在“本期不包含”引用下面追加这些文字。必要完成条件用简短正向表述融入能力范围，具体题目仍按真实边界验收。

下方引用固定开头 `本期不包含：`，多项用顿号分隔：

- PRD：当前全部合格业务功能减去本期已纳入功能。已纳入非 P0 不得再被列为不包含；不生成单个功能内部的部分排除。确无排除写 `本期不包含：无`。
- 说明文档：只写原范围内部或用户明确排除的业务功能；未提供时写 `本期不包含：来源未明确列出`，不能把未知改成无。两条入口均不将已判定的工程测试或策略手段列为排除项。

## 三、评测标准

标题后原生嵌套无序列表，文字原样：

- 进行端到端评分
  - 准确识别用户意图，执行成功且无事实性错误，执行返回的结果满足全部要求记为 1；
  - 确认任一必需条件不满足记 0；

随后三列表格：

| 评分方式 | 评分规则 | 评测细则 |
| --- | --- | --- |
| 成功率 | 两项原生无序列表：满足题设全部必需成功条件记 1。／确认任一必需条件不满足记 0。 | 当前项目的通用要求，原生无序列表 |
| 严口径 | 执行成功，耗时低于 SOTA | —— |
| 松口径 | 执行成功，耗时低于 SOTA × 115% | —— |

只有成功率行的“评测细则”动态生成。依据当前范围和服务，归纳正确理解目标/操作、准确传递参数条件/上下文、执行结果与返回数据/状态一致、如实处理失败/无结果/权限边界、遵守授权避免额外操作等可观察要求。按实际功能合并展开、用本期对象和参数具体化，不套其他服务规则；单题细则留给第五部分。

## 四、数据分布

标题后一个独立普通段落，固定句式：

> 本评测集共〈总题数〉题，覆盖〈一级能力数〉类能力以及〈二级使用场景数〉个二级使用场景；广度〈广度题数〉题，厚度〈厚度题数〉题，深度〈深度题数〉题。

数字与中文之间留空格，如“共 80 题”“覆盖 4 类能力”。一级能力数取范围行数；二级使用场景数是 4.3 中各能力下任务场景条目总数，与双层环形图外圈一致，不是二级需求标签数，也不是 4.1 生活/工作场景数。

顺序固定为：H1 → 总述 → 一个原生飞书画板（内含三图）→ 4.1 → 4.2 → 4.3。

画板随正文一起交付，最终通过同一个说明文档链接访问；单独画板链接或本地图片可作辅助证据，但不能替代文档内嵌成品。只有正文和原生画板都实际完成并验收后才能交付为完成版；空画板、待写节点或仅本地预览均保持未完成状态。

### 三图同一画板

用 `lark-doc` 定位/插入文档画板，`lark-whiteboard` 绘制、修改和导出，身份/权限按对应 Lark 技能交由 `lark-shared` 处理。依赖安装提醒由使用者负责，不新增安装关卡。最终必须是同一飞书画板中的三张环形饼图，不能用本地 HTML/其他工具产出的静态图片替代最终画板，也不拆成多个画板。

依据已确认 BMK 数据绘制实际弧度，参考图片仅控制布局、留白、视觉层级，不沿用样例数字。

严格沿用参考图的信息层级：指定标题、中心总数/“评测题目”、上方图例和双环内部标签即可，不额外增加内外圈解释、计算口径脚注或技术说明；统计口径保存在内部规则和数据中。

**上半区，两张等宽并列环形图：**

- 左上角总标题 `〈评测对象名称〉 · 分布概览`。
- 左图 `用户场景分布`：名称/顺序来自 `user_scenarios`，数量/占比来自 `bmk_plan.user_scenarios`。
- 右图 `广度、厚度、深度分布`：按广、厚、深顺序展示确认题量。
- 两图中心均为突出显示的总题数与“评测题目”。
- 各图下方图例含色块、名称、题量、占比，如 `37 题 · 74%`，色块与扇区逐项对应。

**下半区，一张双层环形图：**

- 标题 `〈评测对象名称〉题目分布`，中心为突出总题数及“评测题目”。
- 内圈为一级能力，标签含名称、题数、占比；外圈为所属能力下任务场景，标签也含名称、题数、占比。
- 外圈分组紧贴父级扇区，组内题量之和等于父级。父级能力配色可区分，外圈用对应同色系浅色。

所有图与文字/表格共享同一总量及统计口径；百分比由题数计算，精度统一。四舍五入时保留真实题数和扇区比例，不靠改题数凑 100%。零题维度不绘制虚假面积，图例/表格保留 0。

写入后从实际飞书画板导出预览，核对同一画板三图、上下布局、标题/图例/中心数字、内外圈归属、比例和标签可读性；在文档中验证嵌入位置。以远端实际字体和文字尺寸检查标签是否完全在扇区内，本地预览通过不能代替；必要时只调整文字位置、换行或字号并重新导出，不改确认题量。实际工具可能需要先插入空画板才能取得 token，此时在该 token 写入三图并导出验收，不能为调整步骤额外新建画板。更新时复用原 token。

### 4.1 用户场景

两列表头固定 `用户场景 | 重点功能`。

- 每场景一行，第一列 `〈场景名称〉（〈题数〉题）`，名称沿用确认清单的简短词组或短语标签，顺序不变，题量来自确认 BMK。附加题数不改变状态中的场景名称。
- 第二列一个普通段落，用一句话概括该场景用户要完成的任务及涉及功能，可在句中列举多项能力。根据本期 scope_basis 写，不扩范围；提及权限、澄清等须有当前依据。
- 同功能可用于多个场景，题量按主归属避免重复。更新场景/题量后同步本表与场景图。
- 本小节仅为 H2 标题和两列表格，表后不增加频率、研究来源、划分理由等解释段落；依据保存在内部。各 H2 与正文/表格之间、4.1 表格与 4.2 H2 之间不插入空段落，4.2/4.3 同样紧接。

### 4.2 广度、厚度、深度指令说明

四列固定 `维度 | 数量 | 观测目标 | 覆盖重点`，表头加粗、内容左对齐，按广厚深三行。

第一列同单元格先写维度名，下方原生引用块分别为：

- 广度：`用户场景与指令覆盖`
- 厚度：`长链路执行`
- 深度：`上下文依赖与逻辑推理`

数量读取确认 BMK，0 也如实显示。

观测目标：

- 广度固定：`场景全覆盖：检查不同用户需求和原子能力是否都能在真实业务 Query 中完成。`
- 厚度固定：`一句话交代多件事或多个明确条件，检查能否沿自然业务链路完整执行，并保持对象、参数、状态和前后一致。`
- 深度结合服务写一句：`从用户本次请求及〈附件、业务资源或线索〉推导出〈需要判断的要求、目标或结论〉，落实到〈本期支持的具体任务或操作〉。`明确已知信息、推导内容、结果如何指导任务；“上下文”限本轮材料，不指前轮聊天。不把明确条件照做写成推理；当前不支持深度时如实说明，不编造能力。

覆盖重点每格原生无序列表，最多 4 条，短而清楚：

- 广度从真实用户场景提取需求、对象、必要条件和可观察结果；按真实短任务合理组合 1–2 个原子功能实现全覆盖，不逐功能机械配一道题。适当覆盖有依据的内容不可用、无匹配、重名等业务边界，避免仅换对象重复搜索或大量过简题。
- 厚度提炼单条请求内实际存在的组合任务、顺序/依赖、多条件及状态一致性，确认上步工具结果为何自然成为下步输入，不依赖用户中途回复。
- 深度提炼当前请求、附件、业务资源及工具结果中的推导、消歧、关联、规则应用、权衡或降级机会。

项目内容多则按近似任务合并，不为凑四条新增或遗漏重点。0 题维度不能虚列已规划的覆盖任务。

### 4.3 题目分布

四列表头固定 `能力 | 题目数量 | 场景分布 | 分维度规划`。

- 能力沿用第二部分名称与顺序，每项一行。
- 题目数量为该能力整数题量。
- 场景分布为该能力下全部任务场景的原生无序列表，每项 `〈具体任务场景〉：〈题数〉`；与外圈同数据，不受 4.2 最多四条限制。
- 分维度规划为原生无序列表，依次 `广度：〈题数〉`、`厚度：〈题数〉`、`深度：〈题数〉`，0 也列出。
- 每行场景之和与三维度之和均等于该能力题量。

最后合计行：能力写 `合计`，数量写总题数；场景分布列用普通段落：

> 共〈总题数〉题。广度〈广度总题数〉题（〈广度占比〉%），厚度〈厚度总题数〉题（〈厚度占比〉%），深度〈深度总题数〉题（〈深度占比〉%）。

数字与中文留空格，如“共 50 题。广度 28 题（56%），厚度 12 题（24%），深度 10 题（20%）。”分维度规划列仍列三条总题数的原生无序列表；比例分母为全评测集。

## 五、题目示例

固定 10 道 Golden Case 数据行，无额外汇总行。固定五列表头：

`用户 Query 示例 | 能力标签 | 环境信息 | 指令类别 | 通过标准`

### 字段规则

- **用户 Query 示例**：直接写用户可能通过语音转文字发送的一条自足请求，不加包裹引号、冒号、编号或“用户说”等前缀。广厚深均遵守 Explicit 单轮边界：目标依靠本次请求、附件及可读取业务资源完成，不依赖前轮聊天、用户后续回复/确认。表达自然、多样，保留必要条件；不能全部用同一开头，不将实现术语塞进请求，也不在句末追加“不要承诺会成功”“不要真的加场”“仅用于测试”等评测者/系统口吻的负向免责声明或结果承诺。真实用户本来就会提出的约束（如“不要重复发送”）可以保留。需要附件时，用其内容或用途自然指代，如“我把到场时间和返程安排发你了”“根据我发的安排文档算一下”，默认不写“附件有什么”“附件是什么”“读取附件内容”等脚手架式话术；只有盘点文件本身是用户目标时才例外。默认不构建依赖具体未来日期、实时场次、余票、价格、库存或即时可达性的题目；日期、地点、对象、任务和工具名称在保留的题目中也不能固定前置或固定在同一位置。
- **能力标签**：广度、厚度、深度三者之一，依任务真实结构判断，不按行号或能力名称机械选择。
- **环境信息**：有特殊准备时按“对象＋关键内容或初始状态”写，只补本题相对公共设置的差异；通常一句，多份材料再分条。确实无需特殊准备时写 `—`。具体边界见本节下方写法。
- **指令类别**：使用确认后的二级用户需求标签，多个用顿号 `、` 连接。PRD 照录 PM 名称，说明文档采用规范后经用户确认的标签；不填一级能力或生活/工作场景名称。
- **通过标准**：新建或实质改写时读取包内 [Rubrics编写方法](../materials/方法参考/Rubrics编写方法.md)；纯措辞精简复用已核验依据。根据该 Query 的对象、条件、结果、状态及必要边界动态写原生无序列表，短、清楚、通俗、可观察。所有必需成功条件满足为 1，任一不满足为 0；允许等价正确答案时明确范围。不把用户后续回复/确认或回答后的任务作为成功条件，不能复制泛化标准或要求展示内部推理。

#### 环境信息写法

- **写必要条件**：写清题目依赖的邮件、订单、歌单、文档等对象及其关键内容或初始状态。权限、当前附件、选中项、时间点等，仅在影响本题执行或判分时补充；不逐题罗列通用准备清单。
- **公共设置只写一次**：如有全集共用的账号、工具、默认登录状态等，在第五部分表格前用一段“统一环境说明”集中写准备要求。单题环境只写差异，不重复公共设置；没有需要说明的公共条件时不补泛泛套话。不增加标题层级、表格列或数据行。后续完整评测集沿用该说明，并在交付中指明位置。
- **材料与结论分开**：环境写可供判断的客观内容或初态，线索须能通过本轮附件或本期工具实际取得；仅在准备说明里提到而执行时不可见的线索不够。预期判断、最终结果留在通过标准，不用结论代替材料事实。
- **默认排除时效性题目**：showcase 与完整评测集不构建依赖具体未来日期、实时场次、余票、价格、库存、上映状态或即时可达性才能判分的题目。若本期能力只能用动态资料呈现，改用带时间戳的固定附件/预置快照，考察模型对材料的理解、比较或执行，不把实时变化作为答案依据；无法稳定复现时改题或替换。
- 负向边界说明属于验收信息，不写进用户话术：例如“不要承诺真的会加场”应放在通过标准或内部验收记录，不能作为 Query 末尾的提醒。
- **缺条件先处理**：缺少执行或判分必需的条件时补齐材料要求或改题；`—` 只表示在公共设置下确实无需特殊准备，不表示材料未知或待补。允许既有业务资源，不依赖前轮人机对话或执行中途的用户补答，也不将对话脚本包装成附件。只写准备要求，不把未搭建的资源说成已存在。

### Golden Case 选择与验收

优先展示能有效测能力、用户会自然表达、有真实业务收益的代表任务，覆盖有代表性的本期能力及任务场景。十道示例固定为 4 道广度、3 道厚度、3 道深度，独立于完整 BMK 配比。通过重设计真实任务达到配比，不仅改标签、不为凑数虚构能力。如果本期范围确实无法支撑某维度，说明具体能力缺口并请求处理，不能假称已达到 4:3:3。

零一测试原则上不作主要样例，简单服务有真实目的且能有效测能力的单操作允许。广度例题可采用短任务组合及有依据的业务边界，不将澄清或不可用反馈另列成能力；无匹配、重名澄清不因是负向情形就自动标为深度。自然化不新增动作、不遗漏边界、不改变维度标签，不为语音感故意加错字、重复或口头禅。

按共用总纲依次检查以下三组要求，三组均须满足；单轮是准入边界，不是第四个质量维度，也不能用单轮成立抵消题目或整体质量不足。

**评测边界**：三类题均检查单轮可完成性。单轮内允许多条件、多次工具调用、长链路和基于材料的决策，不能改成十道简单查询。若发现“前文已确认”“收到初版后用户补充”或“先问我的情况再定计划”式依赖，按实际语义改写或替换；不是删除提示词或把缺失前文塞进环境。信息不足边界题的终点限于本轮有依据的判断/反馈，不等待下一轮回答。

**题目质量**：逐题内部完成三维验收：

1. **题目价值**：明确测哪项能力，成功/失败能从结果区分；目标与 Rubric 一致，不靠冗长、假约束充当挑战。
2. **真实性**：措辞、长度、正式程度、信息组织及对当前附件/业务资源的指代符合语境；无统一模板、过度润色或刻意表演。结合 RealUserSim 提炼判断，推断与真实样本证据分清。
3. **业务价值**：按[业务依据：来源选择与补查](用户场景与BMK规划.md#业务依据来源选择与补查)逐题关联已实际读取的可靠来源，核对需求动机、收益与整条业务链路；官网或既有资料不足、特殊组合存疑时定向查官方案例与具体用户反馈，仍不足就改题或替换。历史题或模型推断不能独自证明需求成立；有依据的简单任务也可保留。

任一明显不足就改写或替换，内部记录简短原因。这是入选质量检查，不是被测模型得分 Rubric，不新增列、固定权重、分数阈值或确认轮次。

**整体质量**：逐题有可观察的能力考点，整组不能被大量过简查询占据，也不能用冗长指令、重复操作或多余条件堆出厚度/深度。广度保证有意义的下限，厚深只保留真实任务需要的链路和推理；难度不按篇幅、步骤数或调用次数打分。不新增固定难度比例或阈值。

整组覆盖有代表性的能力与任务，保持任务、对象、表达及边界多样性；十例不承担完整评测集的全量覆盖。

最终核对恰好 10 行、五列完整、指令类别能映射确认需求、维度标注真实、环境按对象及必要内容/初态简写、公共设置只写一次、线索本轮可获取、缺条件已补齐或改题、无特殊准备写 `—`、通过标准列表短且含全部必要条件。跨题检查真实句式、任务考点和难度的差异，去掉只换对象的重复以及无必要的复杂环节，不以机械句式数量验收。文档阶段只生成这十道；交付后收集用户的 showcase 意见，确认后再按评测集生产路由补齐其余题目。

## 六、评测集链接

最后 H1 下放用户提供或已确认属于本期的可点击评测集链接。尚未提供保留本节写 `待补充`；不虚构链接、不为填满此节跳过 showcase 反馈确认、不因此阻塞说明文档交付。后续完整评测集在飞书多维表格写入并验收后，将真实链接回填本节，沿用原说明文档。

## 回读验收、修正与交付

不能将“命令成功”当成“内容和版式正确”。读取实际飞书输出并导出画板预览，检查：

- 标题对象/类型/版本、六个 H1 和三个 H2、顺序及固定文案。
- 范围完整、排除项正确、PM 标签保持、说明文档内部边界未漏；原生表格/引用/单元格无序列表真实存在，列表没有退化为拼接段落。
- 总题量、三维、能力、两套场景统计，4.1—4.3、总述及画板全部一致，外圈比例分母正确。
- 逐项核查范围中的具体行为、明确数量/显示/展开约束与 BMK 实际任务/观察点对应，不能仅凭功能 ID 齐全宣布覆盖；不将相邻但不同状态操作当成同一项考察。
- 三图确实同一画板，上方并列、下方双层、标题/中心/图例/标签可读，没有裁切或拥挤遮挡。
- 十道示例符合单轮评测边界、逐题三维质量合格、每题业务依据可回查且缺口已处理、整组难度/代表性覆盖/多样性适当；全部映射本期支持能力，公共设置与单题差异明确、必要线索本轮可获取，环境不代写结论，Rubric 可判定。
- 需核对是否误用了具体未来日期、实时场次、余票、价格、库存或即时路线；发现题目依赖这类时效事实才能判分时，改用固定快照或直接替换。
- 第六部分真实链接或待补充；输出链接可实际打开/读取。

发现问题修正并复查受影响内容。写入结果不明时先回读定位已创建的文档/块/画板，避免盲重试产生重复。保存实际文档 ID、链接、画板 token、使用方案版本及验收证据。
